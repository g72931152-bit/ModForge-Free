## 2. Найденные проблемы и исправления

### Архитектура движков

**Проблема:** старый путь запуска смешивал режим диагностики/ремонта и лабораторные изменения так, что ModLab концептуально зависел от общего repair pipeline.

**Исправление:** добавлена явная диспетчеризация:

- `VA2` → `run_va2_engine()`;
- `VE1` → `run_ve1_engine()`;
- `/lab/*` → только VE 1;
- финализация VE 1 → отдельная `finalize_ve1_job()`.

VA 2 и VE 1 имеют разные engine id, версии, состояния, API и отчёты.

### VE 1 зависел от настроек VA 2

**Проблема:** ранее `build_modification_plan()` мог отфильтровать VE 1-изменение через VA 2 `repair_actions`. При выключенных repair actions корректное изменение VE 1 возвращало ошибку 422.

**Исправление:** VE 1 больше не подчиняется флагам ремонта VA 2.

**Регрессия:** добавлен отдельный тест `test_ve1_modification_ignores_va2_repair_action_toggles`.

### Cooldown блокировал event loop

**Проблема:** синхронный `time.sleep()` внутри общего контрольного пути мог удерживать worker/event loop при ожидании снижения нагрузки.

**Исправление:** добавлен асинхронный `load_cooldown_async()` с короткими `await asyncio.sleep(...)`; синхронный guard используется только внутри выделенного worker-потока.

### Cooldown оставлял состояние задачи

**Проблема:** после отмены/паузы во время ограничителя нагрузки внутреннее состояние cooldown могло остаться зарегистрированным.

**Исправление:** добавлена централизованная очистка состояния в `finally` и отдельный lock для load-guard.

### Большие файлы не имели полноценного resource guard

**Проблема:** старый поток обработки крупных ресурсов был ограничен размером чанка, но не умел сам учитывать текущее давление CPU/диска и временно уступать ресурсы.

**Исправление:** для больших файлов введён отдельный bounded worker-path, который на границах работы проверяет host pressure и может переводить задачу в cooldown без потери рабочей копии.

### `lab_ready` не восстанавливался как полноценное рабочее состояние

**Проблема:** после рестарта backend готовая VE 1 лаборатория могла потерять редактируемое состояние или трактоваться как обычная завершённая задача.

**Исправление:** `lab_ready` теперь является сохраняемым состоянием. Рабочая копия и каталог сохраняются, после рестарта runtime-события восстанавливаются.

### Потенциальная гонка при записи результата

**Проблема:** конкурентные записи с одинаковым canonical path могли перезаписывать уже созданный результат.

**Исправление:** `_commit_staged_file()` использует эксклюзивный временный файл и безопасный hard-link fallback вместо слепой перезаписи.

### Слишком тяжёлый polling

**Проблема:** передача полного отчёта вместе со статусом могла увеличивать каждую polling-ответную нагрузку до мегабайт и провоцировать таймауты.

**Исправление:** `/api/jobs/{id}` возвращает компактный progress/status payload; полный отчёт загружается отдельно после готовности.

### Сохранение одиночных файлов

**Проблема:** выбор расширения для некоторых single-file входов был недостаточно устойчивым.

**Исправление:** нормализована логика `save_single()`.

### Нагрузочный cooldown должен быть отменяемым

**Проблема:** pause/cancel могли пересекаться с ожиданием нагрузки.

**Исправление:** cooldown регулярно проверяет cancel/pause и гарантированно освобождает своё внутреннее состояние.

### Перегруженный интерфейс

**Проблема:** во время обработки одновременно показывалась слишком большая часть этапов и служебных данных.

**Исправление:** основной экран показывает только процент, текущую операцию, соединение и действие; список этапов скрыт по умолчанию и открывается через `Показать этапы`.

### Неудобная справка по UI

**Проблема:** второстепенные объяснения приходилось искать в отдельных подсказках.

**Исправление:** добавлен отдельный центр **«Интерфейс»** с навигацией по тематическим разделам и подробным описанием элементов.

### Несогласованные названия и номера релиза

**Проблема:** в проекте оставались старые `0.57-A`, `Mod Lab`, `ModLab` и повторяющиеся обозначения версии.

**Исправление:** текущий релиз унифицирован как `v1 (0.58-A)`, основной движок — `VA 2 · Verification Architecture · 0IN-1.0`, лаборатория — `VE 1 · Variant Engineering · M0-D-l00`. Старая формулировка ModLab убрана из пользовательского интерфейса.

### Service-worker/cache contract

**Проблема:** обновление UI без повышения cache epoch могло оставлять старые JS/CSS в браузере.

**Исправление:** shell/cache/query keys обновлены до `058a`.

### PWA имя

**Проблема:** версия релиза могла попасть в имя установленного приложения и создавать лишние дубликаты при обновлениях.

**Исправление:** display name PWA снова стабилен как `ModForge`, версия отображается в самом интерфейсе.

## 4. Новая архитектура

### VA 2 · 0IN-1.0

`intake → security → catalog → analysis → repair preview → repair → recheck → health/diff/report → package`

Рабочая копия отделена от исходника. Большие файлы проходят потоковый путь. Нагрузка ограничивается через load guard.

### VE 1 · M0-D-l00

`prepare → catalog → persistent lab_ready → targeted mutations → stress checks → scoped verification → package`

Полного VA 2 pipeline здесь нет. VE 1 не использует VA 2 repair action toggles.

### Автоматический регрессионный набор

### Синтаксис

- `python -m py_compile main.py` — OK.

### Полный стресс-набор

`tests/full_stress_v058a.py` покрывает:

1. `/api/health` и `/api/engines`;
2. VA 2 Standard;
3. VA 2 Aggressive + точный процентный парсер;
4. restart/re-check;
5. VE 1 paint + physics + stress + отдельная finalize;
6. malformed ZIP + path traversal;
7. сохранение `lab_ready` через перезапуск backend;
8. реальный ZIP с большим членом **520 МиБ**, превышающим порог 512 МиБ, потоковый worker и проверку скачивания результата;
9. headless UI smoke центра интерфейса, горячих клавиш и новых названий.

Во время реального stress-run серверные секции **1–8 завершились успешно**, включая создание и обработку 520 МиБ ресурса и восстановление VE 1 через рестарт.

UI smoke в исходном исполнении стенда был ограничен политикой самого Chromium для loopback-навигации (`ERR_BLOCKED_BY_ADMINISTRATOR`), поэтому он не засчитывался как живой HTTP smoke. Для окончательной проверки был использован DOM-level smoke на том же `index.html`/`styles.css`/`app.js` с изолированным browser storage shim; это проверяет фактическую разметку и frontend-код без обхода application logic.

## 6. Известные ограничения

- BeamNG.drive runtime не запускается внутри сервера.
- Сложная неизвестная Lua-логика не исполняется и не «угадывается».
- Эвристические JBeam-исправления требуют проверки в игре.
- Для Render и других эфемерных платформ восстановление задач после redeploy зависит от наличия постоянного storage.

## 7. Итог

Текущий проект собран как **v1 (0.58-A)** с двумя независимыми engine contracts:

- **VA 2 · Verification Architecture · 0IN-1.0** — диагностика и безопасный ремонт;
- **VE 1 · Variant Engineering · M0-D-l00** — отдельная лаборатория вариантов.

Ветка больших файлов и восстановление задач проверены реальными stress-сценариями. Автоматические тесты проходят, а ограничения, которые нельзя доказать без запуска самой игры, прямо указаны в README.
